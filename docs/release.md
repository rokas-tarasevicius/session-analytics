# Releases and distribution

Every release is one compiled package, `session-analytics-X.Y.Z.tgz`, built from the released commit by `scripts/build.ts` and packed from `dist/`. The GitHub Release receives those bytes after the release workflow has installed and run them, and npm and the Homebrew tap receive the same bytes once their [one-time setup](#one-time-maintainer-steps) is done. The root `package.json` stays `private: true` with the TypeScript bin, so a contributor's `npm link` keeps running the live source and the source layout cannot be published by accident; only the generated `dist/package.json` describes the installable package. Users install as described in [installation](cli.md#install).

## Validate a candidate

From a clean checkout of the candidate commit:

```bash
npm ci
npm run release:check
npm run demo
```

`release:check` checks version agreement, types, tests, public snapshot schemas, a synthetic JSON report containing all six providers and private-fixture sentinel absence. It then builds the compiled package into `dist/` (`npm run build`), packs it, and checks the tarball: every entry point and worker, the bundled runtime's bootstrap, every file the dashboard serves, the font license, brand notice, rate card, schemas and skill, and no TypeScript, declaration, source map, dotfile or local data. The generated manifest must match the source version, name a `.js` bin with a `node` shebang, require Node.js 24 on macOS and Linux, and declare no scripts or dependencies. Finally `scripts/smoke-installed.ts` installs the tarball with `npm install --global --ignore-scripts --offline` into a temporary prefix whose path contains a space and runs it from there: help and version for every command, the synthetic report (compared with the source run, including Cursor sessions from their separate worker, and failing on any warning that a synthetic source could not be read), an MCP tool call, the dashboard with every static file and API route reporting the expected version, a clean stop on `SIGTERM`, a saved machine read through a stand-in `ssh` (`test/fake-ssh.ts`) with the bundled runtime, which the installed bin packs from its own compiled files, installs under a separate home and then runs again from the verified copy, and the report again from a read-only installation. It prints the tarball's SHA-256 and npm integrity. `npm run release:check -- --port PORT` fixes the smoke's dashboard port; otherwise it takes a free one. `node scripts/smoke-installed.ts session-analytics@X.Y.Z` runs the same smoke against a registry install and hashes the tarball npm downloaded. `release:check` does not tag, publish, change repository settings or read real history.

`npm run pack:release` writes the same tarball to `release/`. The index fingerprints the code that runs, so the first scan after an upgrade parses present sessions again, and so does every switch between a checkout and an installed copy that share a data directory; give a checkout its own (see [from source](cli.md#from-source)).

For browser validation, start `npm run demo -- --no-open` and exercise all seven views, repository focus, provider filters, window selection, keyboard navigation, dialogs and exports in both themes. Check a narrow viewport and a laptop viewport, including empty windows and shared snapshots. Use synthetic data for every screenshot and reproduction. [Branding](branding.md#regenerating-images) documents the screenshot assets.

Run `npm run test:browser` for the required automated Chrome suites. On Linux, set `SESSION_ANALYTICS_CHROME` to the Chrome/Chromium executable; macOS defaults to the Google Chrome application path. This command isolates temporary fixtures and fails if Chrome is missing or cannot launch. The general source suite also runs these browser suites when Chrome is installed, including on hosted macOS; it may skip them only when Chrome is unavailable. The dedicated Ubuntu browser job remains mandatory regardless of whether the source suite ran Chrome.

The release version must agree in `package.json`, `package-lock.json`, `src/version.ts` and the latest release section in `CHANGELOG.md`. The release policy chooses the section's date; the metadata check does not validate that date. The release is tagged `vX.Y.Z` for that version; prerelease versions are refused. The changelog must also end with compare links for the release: `[Unreleased]: https://github.com/rokas-tarasevicius/session-analytics/compare/vX.Y.Z...HEAD` and an `[X.Y.Z]:` link ending at `vX.Y.Z`.

## Cut a release

Releases follow the [Conventional Commit](https://www.conventionalcommits.org/en/v1.0.0/) titles of the pull requests merged to `master`, which become their squash commits:

| Title | Next version |
| --- | --- |
| `feat: …` or `feat(scope): …` | minor (0.10.3 → 0.11.0) |
| `fix: …`, `perf: …` | patch (0.10.3 → 0.10.4) |
| `type!: …`, or a `BREAKING CHANGE:` footer | major (1.4.2 → 2.0.0); before 1.0.0, minor |
| `docs`, `test`, `ci`, `chore`, `refactor`, `build`, `style`, or not a Conventional Commit | none |

1. Merge pull requests as usual, with user-facing notes in `CHANGELOG.md`'s `Unreleased` section.
2. After each merge, the **Release PR** workflow (`.github/workflows/release-pr.yml`) runs `scripts/release-prepare.ts`. It finds the highest bump among the titles since the last release tag. Then it rebuilds the branch `release/next` from `master` with the version set in `package.json`, `package-lock.json` and `src/version.ts`, and `Unreleased` moved to `## [X.Y.Z] - YYYY-MM-DD` with its compare links; on a new minor or major version, it also updates [SECURITY.md](../SECURITY.md)'s supported versions. It opens or updates one pull request, `chore(release): X.Y.Z`, and dispatches CI on it, because a branch the workflow token pushes starts no workflows by itself. When `Unreleased` is empty, it writes notes from the titles instead. With nothing releasable, there is no release pull request.
3. When you want to release, review that pull request's notes and merge it. The merge releases it: the [release workflow](#the-release-workflow) sees that `vX.Y.Z` is not tagged yet, runs every check on the merged commit, tags it `vX.Y.Z` and publishes. Watch it with `gh run list -w Release -L 1` and `gh run watch`. Nothing else is needed: no tag is pushed by hand.

To change the notes, edit `Unreleased` on `master` (the release pull request is rebuilt from it). To change the version, fix the titles' types, or release by hand: a pull request that sets the version and changelog section itself, as `node scripts/release-prepare.ts --write` would, releases on merge the same way. `node scripts/release-prepare.ts` without `--write` prints the next version.

A merge that leaves the version unchanged releases nothing, so ordinary pull requests never publish. Should the release's checks fail before it is tagged, merge the fix without another version bump: the next push to `master` finds the version still untagged and releases that commit instead.

### Dry run

```bash
gh workflow run release.yml --ref master
gh run watch
```

A manual run of the release workflow is a dry run of releasing that commit, on any branch. Its `plan` job takes the tag name from `package.json` (`v` and its version) and checks that the tag does not exist yet; then it runs `validate` on Ubuntu and macOS (the tag and release notes check against that name, then `npm run release:check`), `browser`, `package` and every `smoke` leg exactly as a release does, so while `HOMEBREW_TAP` is `true` the macOS leg under Node.js 26 also checks the Homebrew formula's style; its `release` artifact keeps the tarball, `SHA256SUMS` and notes for 7 days. `release`, `npm` and `homebrew` run only for a push to `master`, so a dry run has read-only repository permission, enters no environment, sees no secret and publishes nothing. An existing tag fails the dry run, because a released version can never be tagged again: bump the version first.

A passing dry run shows that the version metadata, changelog section and compare links agree, that the checks pass on both platforms and in Chrome, that the packed tarball installs and runs on every operating system and Node.js leg, and, while the tap is on, that the Homebrew formula for that tarball passes `brew style`. It does not exercise anything after that: the REST calls that create, fill and publish the GitHub Release and the provenance attestation, npm's trusted publishing and the registry install, or the Homebrew install, test and `brew audit --strict` of the published asset and the push to the tap, nor the environments, variables and deploy key they use. `brew style` also leaves out the `FormulaAuditStrict` cops that `--strict` adds to the audit. A release runs them for the first time; re-running them is safe (see [below](#the-release-workflow)).

## The release workflow

`.github/workflows/release.yml` runs on every push to `master`, and by hand as a [dry run](#dry-run), with read-only repository permission by default. Pushes to `master` have one run at a time, never cancelled once started; GitHub keeps only the newest waiting run, so a push that lands while another waits replaces it. No release is published twice and the newer commit contains the older one, but should both commits bump the version, the first bump is never released: merge one version bump at a time and let its run start first. Dry runs queue apart from pushes, so they never delay a release's run or re-run; a newer dry run on the same ref replaces one that is still pending. Every action is pinned to a full commit SHA.

| Job | Runs on | What it does |
| --- | --- | --- |
| `plan` | Ubuntu | Always runs first. Names the release `v` and `package.json`'s version and reads its tag: untagged, a push releases this commit and a dry run checks it; tagged at this commit, a push resumes that release; tagged at another commit, a push changed no version, so every later job is skipped, and a dry run fails. |
| `validate` | Ubuntu, macOS | Checks the tag and release notes, then `npm run release:check`, including the installed smoke of a locally built tarball. |
| `browser` | Ubuntu | Required Chrome suites; a missing Chrome fails. |
| `package` | Ubuntu | `npm ci`, the notes check and `npm run pack:release`; copies the tarball to the unversioned alias `session-analytics.tgz`, writes `SHA256SUMS` for both, and uploads them with the release notes as a workflow artifact kept for 7 days. |
| `smoke` | Ubuntu, macOS × Node.js 24.0.0, 24, 26 | Downloads the artifact, verifies `SHA256SUMS`, and runs `scripts/smoke-installed.ts` on that exact tarball. Node.js 24.0.0 is the oldest version `engines` allows, 24 the newest 24.x, and 26 Homebrew's `node`. The checkout supplies only the smoke script, the formula script, demo and test fixtures. While `HOMEBREW_TAP` is `true`, the macOS leg under Node.js 26 then renders the Homebrew formula for that tarball, as the `homebrew` job would, and runs `brew style --formula` on it in a throwaway local tap, so a formula that Homebrew's style cops reject fails before anything publishes. A prerelease skips the check, because it leaves the tap alone. |
| `release` | Ubuntu | Tags the commit and publishes the GitHub Release. Runs only for a push to `master` that `plan` releases, when `validate`, `browser`, `package` and every `smoke` leg succeeded and the run was not cancelled. |
| `npm` | Ubuntu | For a release, publishes the same tarball to npm when the repository variable `NPM_PUBLISH` is `true`. |
| `homebrew` | macOS | For a release, when the repository variable `HOMEBREW_TAP` is `true`, installs, tests and audits the rendered formula with Homebrew, then updates the tap. |

Every job that downloads the artifact verifies `SHA256SUMS` before using it. Only `release` has `contents: write`, and with `id-token: write` and `attestations: write` it attests build provenance for the tarball (`gh attestation verify session-analytics-X.Y.Z.tgz -R rokas-tarasevicius/session-analytics`). It runs no repository code: REST calls with the workflow token create the tag `vX.Y.Z` at the commit the run checked, or find it there on a re-run, and stop if it names any other commit; then they create the release as a draft, or resume this tag's draft on a re-run, upload `session-analytics-X.Y.Z.tgz`, `session-analytics.tgz` and `SHA256SUMS`, check each upload against the verified file, and only then publish the release. It is marked latest unless the current latest release has a higher version, so a backport or a late re-run never moves `/releases/latest/download/session-analytics.tgz` back. That URL also never names a release without files. A published release is never changed: a re-run succeeds only when it already carries identical files.

The `npm` job runs after the GitHub Release in the `npm` environment with `id-token: write` and read-only contents. It installs npm 11.21.0 (trusted publishing needs 11.5.1 or newer) and runs `npm publish` on the release tarball with dist-tag `latest`, or `backport` when the registry's `latest` is already a higher version: an explicit `--tag` turns off npm's own guard against tagging an older version `latest`. Trusted publishing exchanges the job's OIDC token for a short-lived credential and adds provenance, so no npm token is stored. A re-run finds the same bytes already published and skips the publish. The job then waits up to 10 minutes, since the registry can take several to serve a new version, until `npm view --prefer-online session-analytics@X.Y.Z dist.integrity` equals the tarball's SHA-512 integrity, and runs the installed smoke against `session-analytics@X.Y.Z` from the registry.

The `homebrew` job runs on macOS in the `homebrew` environment after the GitHub Release, and after `npm` when that job ran. `scripts/homebrew-formula.ts` renders `Formula/session-analytics.rb` from the version and the tarball's SHA-256. The job copies it into a throwaway local tap (`brew tap-new --no-git`) and runs `brew install`, `brew test` and `brew audit --strict` on it, because the tap's own CI checks the formula only after this job has pushed it to `main`. Then it pushes the formula to `main` of [rokas-tarasevicius/homebrew-tap](https://github.com/rokas-tarasevicius/homebrew-tap) over SSH with the `TAP_DEPLOY_KEY` deploy key, the only secret in the workflow and visible only to that step. The step writes the key to a private temporary file that it removes however it ends, trusts only github.com's host keys as GitHub publishes them (`gh api meta --jq .ssh_keys`), shallow-clones `main` when it is the tap's default branch (or starts `main` in an empty tap, and otherwise stops without a commit, because `brew tap` reads only the default branch), and commits as `github-actions[bot]` with the message `session-analytics X.Y.Z`. An unchanged formula makes no commit, and a tap that already has a higher version is left unchanged. Should GitHub rotate a host key, update the pinned keys in the step and the fingerprints in `test/integration-release.test.ts`. The formula installs the release tarball with `npm install *std_npm_args`, depends on Homebrew's `node`, and pins that Node.js ahead of any older one on `PATH`. Its test runs `--version` and an offline `report --json --no-index` with an empty `HOME`. The script is the formula's only source; the tap's copy is overwritten on each release.

With neither variable set, a release still produces a complete GitHub Release, and the tarball URL install works. With `HOMEBREW_TAP` set, the formula's `brew style` check in `smoke` gates every channel: should a Homebrew update on the runner add a style cop that rejects the formula after the dry run passed, the release's run fails before anything publishes or is tagged, and a re-run renders the same formula from the same commit and fails the same way. Fix `scripts/homebrew-formula.ts` and merge the fix: the version is still untagged, so that merge releases it. `release:check` refuses prerelease versions today; should it allow one, the workflow would publish a GitHub prerelease that is not marked latest, use npm's `next` dist-tag and leave the tap alone.

An active [tag ruleset](https://github.com/rokas-tarasevicius/session-analytics/rules/24996643), configured and read back on 2026-10-13, blocks updates and deletion of `refs/tags/v*` with no bypass actors. This keeps a release tag from moving once the workflow has created it. When a release's run fails, re-run the failed jobs from its Actions page. Re-running is safe: a release, npm version or formula that already has these bytes is left alone, and a tag that publishes after a higher version never takes over `latest` on GitHub, npm or the tap. A failure before the `release` job tags the commit is fixed by merging the fix, which releases the same version from the new commit. One such failure is the tag itself: GitHub can refuse the workflow token a tag on a commit whose `.github/workflows` files differ from `master`'s, as when a later merge changed a workflow during the run; re-running cannot help, but the next push to `master` releases the version from its own commit. A failure after it that needs a code change takes the next patch version, because the tag cannot move; a formula the `homebrew` job rejected is the exception, recovered in the tap as described [after release](#after-release).

## One-time maintainer steps

These account and repository actions turn on the npm and Homebrew jobs. Until they are done, those jobs are skipped, and the user guides (README, `docs/cli.md#install`, the FAQ and the agent skill) name only the release tarball. Add each channel's install, upgrade and uninstall commands to those guides only after it serves a release, so no guide sends users to a package that does not exist or that someone else could register.

### npm

1. Create or verify an npm account with two-factor authentication, preferably a security key.
2. Release the first packaged version with `NPM_PUBLISH` unset, and claim the name immediately after: download `session-analytics-X.Y.Z.tgz` and `SHA256SUMS` from its GitHub Release, run `shasum -a 256 -c --ignore-missing SHA256SUMS`, then `npm publish session-analytics-X.Y.Z.tgz` with your second factor. This claims the unscoped name with the bytes CI tested; that version has no provenance. Until then anyone can register `session-analytics`, so check `npm view session-analytics maintainers` names only you.
3. On npmjs.com, open the package's **Settings → Trusted publishing** and add GitHub Actions: owner `rokas-tarasevicius`, repository `session-analytics`, workflow `release.yml`, environment `npm`. Leave **Allow npm dist-tag** off: `npm publish --tag` sets `latest` or `next` itself, and you can move a dist-tag with `npm dist-tag add session-analytics@X.Y.Z latest` and your second factor. Then set **Publishing access** to require two-factor authentication and disallow tokens.
4. In the repository settings, create the environment `npm` and limit its deployments to the `master` branch. Requiring your review there would hold every release's npm publish until you approve it.
5. Set the repository variable `NPM_PUBLISH` to `true`. The next release publishes through CI.
6. Add the npm commands (`npm install -g session-analytics`, pinning with `@X.Y.Z`, `npx session-analytics@X.Y.Z`) to the user guides.

### Homebrew

1. Create the public repository `rokas-tarasevicius/homebrew-tap`. Publishing the scaffold of `brew tap-new rokas-tarasevicius/homebrew-tap` gives it a `main` branch and Homebrew's syntax check: `gh repo create rokas-tarasevicius/homebrew-tap --public --source "$(brew --repository rokas-tarasevicius/homebrew-tap)" --push`. An empty repository, or one with only a README on `main` as its default branch, also works: the first release adds `Formula/session-analytics.rb` to `main`. `brew tap` reads only the default branch, so a tap whose default branch has another name fails the job and receives no commit.
2. Create an ed25519 key pair without a passphrase, for example `ssh-keygen -t ed25519 -N '' -C 'session-analytics release' -f tap-deploy-key`, and add the public half to the tap as a deploy key with write access: `gh repo deploy-key add tap-deploy-key.pub --repo rokas-tarasevicius/homebrew-tap --allow-write --title 'session-analytics release'`. A deploy key can write to that one repository only, so no personal access token is needed.
3. In this repository, create the environment `homebrew` and limit its deployments to the `master` branch. Store the private key as its secret `TAP_DEPLOY_KEY`: `gh secret set TAP_DEPLOY_KEY --env homebrew --repo rokas-tarasevicius/session-analytics < tap-deploy-key`. Then delete both key files.
4. Set the repository variable `HOMEBREW_TAP` to `true`. The next release commits the formula. For a release that is already published, commit the formula yourself: run `node scripts/homebrew-formula.ts --version X.Y.Z --sha256 <SHA-256 from SHA256SUMS>` and save its output as `Formula/session-analytics.rb` in the tap.
5. Check the result with `brew install rokas-tarasevicius/tap/session-analytics` and `brew test session-analytics`, then add the Homebrew install, upgrade and uninstall commands to the user guides.

## Public launch gates

The maintainer made the repository public on 2026-10-13. These repository settings were configured and read back then; recheck them after any change:

- **Required checks.** Branch protection on `master` requires `check (ubuntu-latest)`, `check (macos-latest)` and `browser (ubuntu-latest)`, with up-to-date branches, pull requests and resolved conversations. It applies to administrators; force pushes and deletion are disabled. Pull requests, pushes to `master` and manual runs use GitHub-hosted runners only, regardless of repository visibility; both `check` jobs run `npm run release:check`, so every pull request builds, installs and runs the package on Linux and macOS. No workflow selects `agentbox` or treats a platform as advisory.
- **Review and code security.** Since 2026-10-20 the ruleset "Maintainer review on master" also requires one approving review from a code owner (`.github/CODEOWNERS`), with stale approvals dismissed and the last push approved by someone else; repository administrators may bypass it, only through a pull request, so the maintainer merges their own pull requests with `gh pr merge --squash --admin`. Only squash merges are allowed and merged branches are deleted. Secret scanning with push protection, Dependabot alerts and security updates are on; every action must be pinned to a full commit SHA; workflows from any outside contributor's pull request wait for approval. GitHub Actions may create pull requests, for the release pull request; an approval from a workflow never counts, because only a code owner's does.
- **Runners.** The repository runners API listed zero available self-hosted runners on 2026-10-13. Recheck repository access and any inherited runner policy before adding one: an outside contributor's workflow could otherwise select it. [GitHub Actions security guidance](https://docs.github.com/en/actions/reference/security/secure-use).
- **History and assets.** The [2026-10-13 history review](proposals/evidence/public-history-review-2026-10-13.md) records the reachable text, image and font inventory and its limits. Recheck any added refs or assets. Removing a file from the latest commit does not remove it from history.
- **Private vulnerability reporting** was enabled after the visibility change and read back through GitHub's settings API. Independently check that an ordinary signed-in user can open the route in [SECURITY.md](../SECURITY.md). [GitHub configuration instructions](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository).
- **Private reporting contacts.** [CODE_OF_CONDUCT.md](../CODE_OF_CONDUCT.md) and [SECURITY.md](../SECURITY.md) name the maintainer's existing public email address and recipient. Ownership and publication were verified against the maintainer's public website source; no test email was sent. The maintainer must monitor the mailbox.
- **Social preview.** Upload `assets/social-preview.png` in repository settings; this is still open in [TODOS.md](../TODOS.md).

## After release

Check each channel from a clean shell: `npm install -g https://github.com/rokas-tarasevicius/session-analytics/releases/latest/download/session-analytics.tgz` and `session-analytics --version`, `npm view session-analytics version` once npm publishing is on, and `brew upgrade session-analytics` once the tap is. Recheck the private reporting routes. For an accounting regression, record which totals move and why in the next changelog entry. For a privacy or security issue, follow [SECURITY.md](../SECURITY.md) and withdraw affected release guidance while triaging.

When the `homebrew` job's `brew install`, `brew test` or `brew audit --strict` fails, the GitHub Release and npm stand and the tap keeps its previous formula. Re-run the job first: a passing re-run, as after a failed download of the release asset, needs nothing more. When the formula itself is at fault, a re-run renders the same formula from the released commit and fails the same way, so fix `scripts/homebrew-formula.ts` on `master` instead (v0.10.0's formula failed `brew audit --strict` because Homebrew's style cops now want `formula_opt_bin("node")` instead of `Formula["node"].opt_bin`), then render the released version with the fixed script: `node scripts/homebrew-formula.ts --version X.Y.Z --sha256 <SHA-256 of session-analytics-X.Y.Z.tgz in the release's SHA256SUMS>`. Commit its output to the tap as `Formula/session-analytics.rb`, on `main` or through a pull request. The tap's own CI installs, tests and audits it (`brew audit --strict --online`) on macOS and Linux; check that it passes, then `brew upgrade session-analytics`. The next release renders with the fixed script, so the tap needs nothing more. A fault in the released package rather than its formula cannot be fixed in the tap; it takes the next patch version, like any other code change.
